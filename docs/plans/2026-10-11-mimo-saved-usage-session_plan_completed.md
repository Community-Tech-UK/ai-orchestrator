# MiMo usage without a Chrome profile

Status: implemented and verified; closed subject to the genuine human/Xiaomi live checks linked below. Untracked; no commit or branch authorised.

## Intent and design

James wants the OpenCode/MiMo account usage meters to update without maintaining a separate Chrome profile for each account. Existing usage/detail endpoints require a Xiaomi console session, not the model API key. Use an account-isolated, sandboxed Electron sign-in window only when James clicks Connect usage; store the console and Xiaomi SSO cookies encrypted with the existing OS-backed safeStorage accessor. Poll the existing read-only endpoints through Node fetch after the window closes. Never store passwords or send cookies across IPC. Chrome-linked accounts retain their existing reader until a saved session is connected. Saved sessions take precedence and never fall back to another account on rejection.

## Risks and boundaries

Xiaomi may reject embedded login or require a human verification challenge; do not automate around that. Initial sign-in and a real account's restart/renewal need live validation. Session storage must fail closed if OS encryption is unavailable. Asynchronous login and quota refresh must not resurrect disconnected sessions or attach one account's usage to another. No dependencies, branches, commits, pushes or deployment.

## As-built notes

- The user chooses Connect usage for a MiMo account. Its sandboxed sign-in window has no preload, Node access, permissions, popups or downloads; navigation is limited to exact Xiaomi HTTPS origins. Only complete, scoped console/SSO cookies can be saved, encrypted through OS storage outside the repository. The window closes after saving. Passwords are not stored; credentials do not cross IPC.
- Background quota reads and renewal use the saved account session through existing Node HTTP code. Saved credentials take precedence and remain authoritative when expired, malformed or rejected. A disconnected account may use its explicit existing Chrome fallback; an account with no fallback receives Connect usage guidance. Source/generation invalidation prevents old figures, renewals or login captures restoring a disconnected account.
- Temporary login sessions use at most eight stable in-memory partitions, matching the provider account limit. Every exclusive lease awaits prior storage/auth/connection cleanup. Disconnect cancels preparation. Disposal is idempotent and destroys the window before release, bypassing page close vetoes. Failed/timed-out cleanup blocks reuse. Permanent denial handlers are installed once per bounded slot; account capture listeners are detached through a retained WebContents emitter on release, including human-closed windows whose native BrowserWindow getters are already invalid.
- The Accounts settings template was extracted into a separate HTML file to meet the existing TypeScript size gate. Rendered component checks exercise Connect/Disconnect usage independently of CLI sign-in, including disabled accounts. The production Angular build covers template wiring.
