### Deviations from the step text, and limits (plain)

1. **The conversation ledger is not used.** The step says the ledger answers "latest user or Harness input". In this code the ledger only receives messages for chat-linked sessions or providers with context-evidence capture turned on (default off: `chat-transcript-bridge.ts` drops the batch when there is no chat and evidence mode is `off`), so an ordinary parent session's messages are not there. The registry above is fed by the one funnel every send passes (`InstanceManager.sendInput`) and gives the same answer, in memory. Because that is synchronous, the check does not need to be asynchronous; it still runs before the general authority check.
2. **Inputs that do not pass through `InstanceManager.sendInput`** (re-sends after a provider limit or account switch, history replay, the initial prompt, runtime-change notices, orchestrator responses) do not replace the latest input directly. They are caught by the turn count when they start a turn. One that joins a turn already running without starting a new one would not be seen.
3. **A queued typed message restored after an app restart** (the durable queue row is not extended) counts as not typed by a person. That fails safe.
4. **Boot recovery still lands an interrupted "Land anyway" as an ordinary landing** (it re-queues without the override), as before; unchanged and not part of this step.
5. **Claude's turn identity comes from the CLI's own `command_lifecycle` lines (verification round 3).** Probed 8 November 2026 against Claude Code 2.1.319 with a scratch `claude -p --input-format stream-json` process: a user message carrying a `uuid` is followed by `command_lifecycle` lines naming it (`queued`, `started`, then `completed` after the `result`), and `started` comes immediately before that turn's `init`. A turn the CLI began by itself after a background job ended (the second `init` in the probe) had no `command_lifecycle` lines at all. This is the identity the earlier order-based attribution lacked.
6. **Claude attribution is now by identity, not order.** Every message Harness writes (`InputFormatter.sendMessage`, and the adapter's `sendRaw` path) carries a `uuid` from `ClaudeTurnStartTracker.claimWrite()`; `ClaudeCliAdapter.processCliMessage` passes `command_lifecycle` lines to the tracker; an `init` is reported as `harness-send` only when the `started` line before it named a uuid Harness wrote, and as `provider` otherwise. So a provider turn that begins after the person's message is written but before the person's own turn is reported as `provider` (it is counted and ends the message's wait, as before), and the call is refused. A message written while a turn runs is now attributed correctly too (it gets its own `started` and `init`). A `started` line with no `init` of its own (a message folded into the running turn) is cleared by the next `result` or `completed`, so it cannot label a later provider `init`; that message is simply never bound, which refuses. The finished-background-work notice is still reported as a provider start (the CLI may fold it into a running turn with no `init`). What remains for the live-test document: the same probe inside the real app, and that the CLI never runs a person's message with no `started` line.
