# Diagnostic credential exposure

A process-ownership inspection on 31 October unexpectedly returned a session-specific tool capability in an npm process title. Its value appeared in one tool response. It is deliberately not repeated here. The initially saved ignored ownership diagnostic was immediately rewritten with credential-like assignments redacted before being preserved in this evidence folder. No credential value was added to source, tests, committed files or this report.

The code in `src/main/mcp/orchestrator-tools-rpc-capability.ts` derives the token from a process-local secret and the instance identity; `orchestrator-tools-rpc-server.ts` also checks that the caller remains known. No per-instance rotation/revocation tool was found through the available tool discovery routes. The credential has not been claimed revoked. Removing the owning worker session invalidates its known-instance access; restarting Harness changes the process secret. Neither action was performed during active repair, because the AIO lifecycle owns this worker and other sessions must be preserved. Normal owner-managed removal after handover remains required.

The inspection then used filtered, known parent/child identity and working-directory checks without redisplaying credential values. Only the verified Vitest child for the superseded `integrated-2` run received SIGINT. The command finished with exit130 and its recorded children were absent afterward. The regular ps probe returned EPERM; this did not establish that any host/service was down. No unrelated process was signalled.
