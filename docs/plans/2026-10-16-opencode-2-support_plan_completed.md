# OpenCode 2 support in Harness

Status: Completed on 16 October 2026 for the agreed implementation and agent-runnable verification. Recommendations 1–4 are adopted. Final independent review: PASS with no unresolved actionable findings. Deferred live checks remain in the [live checklist](2026-10-16-opencode-2-support_livetest.md). No commit, push, global installation or deployment was performed.

Related: [LT-705 in the remediation register](livetest-remediation-register.md#lt-705) (why Harness refuses OpenCode 2 today), [OpenCode startup remediation plan](2026-10-13-opencode-startup-remediation_plan_completed.md), [original OpenCode provider plan](2026-09-22-opencode-provider_plan_completed.md).

## Starting point: initial investigation on 16 October 2026

Harness currently refuses to use OpenCode 2 on purpose. When we tried it on 13 October (version 2.0.18), OpenCode 2 sessions ignored the settings Harness hands each session: which MiMo account to use, the reply-length limit and the permission rules. So Harness only runs OpenCode 1.

OpenCode 2 is now properly released (2.0.30, 15 October 2026). I tested 2.0.30 in a throwaway folder today and the main blocker is gone: each Harness session gets its own private OpenCode helper, and that helper does pick up Harness's settings. So supporting OpenCode 2 is now realistic.

It is not a one-line switch, though. OpenCode 2 changed several things Harness relies on:

- It installs under the same `opencode` command name as OpenCode 1, from a different npm package, so installing one can replace the other.
- It keeps API keys in its database, not in the file Harness's sign-in writes to. Accounts added through Harness would not reach OpenCode 2.
- Its model list command no longer gives the detail Harness reads, so model discovery needs reworking.
- It translates Harness's permission rules into a new format. Harness's code for reading them back would currently misread some rules. Its safety check could then either block every session or miss a rule that had been weakened.
- Most helper commands try to talk to the shared background OpenCode service (the one the OpenCode desktop app runs) unless told not to. On this Mac that service is still the older 2.0.18.

There are also worthwhile improvements: cheaper session resume, live sub-agent progress, retry and compaction notices that Harness can show, and a cleaner way to pass Harness's tools to OpenCode.

## Decisions adopted

1. **Direction.** Recommended: make OpenCode 2 the preferred OpenCode in Harness, keep OpenCode 1 working as a fallback until OpenCode 2 has passed live testing, then retire OpenCode 1 in a later plan. Alternative: stay on OpenCode 1 only and do just Phase 0.
2. **Where OpenCode 2 keeps its data.** Recommended: use OpenCode's normal shared database, the same one the OpenCode desktop app uses, so keys and sessions are shared. Alternative: give Harness its own private OpenCode database. That is more isolated, but keys must be added separately and Harness sessions would not show in the desktop app.
3. **Oldest OpenCode 2 version Harness accepts.** Recommended: 2.0.30, the only version proven to work. Phase 0 can find the first fixed version if older installs matter.
4. **Installing OpenCode 2 for you.** Recommended: Harness's provider checkup offers the install but explains that it replaces the OpenCode 1 command, and never installs or upgrades across major versions without asking. Alternative: Harness only tells you the command and you run it.

## Initial Harness gaps (before this implementation)

- `selectOpenCodeLaunch` refuses any major above `MAX_SUPPORTED_OPENCODE_MAJOR = 1` (`src/main/cli/adapters/opencode-cli-launch.ts:23`, check at `:120`). Candidates come from PATH, `/Applications/OpenCode.app/...`, `~/.opencode/bin` and `~/.local/bin` (`:30-60`). It does not look for `opencode2` or the desktop app's `cli/<version>/opencode-cli`.
- Dormant OpenCode 2 branches already exist: probe args `api --standalone GET /api/config` (`opencode-effective-budget-config.ts:15-18`), `normalizeOpenCodeNativeConfig` and `mirrorOpenCodeProviderForV2` (`opencode-v2-config.ts`), plain `acp` with progress observation off (`opencode-child-progress-source.ts:321-324`), and factory switches (`opencode-adapter-factory.ts:194`, `:200`).
- **Gap in the dormant normaliser (found today):** `rulesetToPermission` keys rules by `action` only and drops `resource`. So `shell * ask` followed by `shell git push * deny` collapses to `shell: deny`. It also leaves OpenCode 2 action names (`shell` for `bash`) unmapped. The only runtime permission assertion today is the doom-loop brake (`assertOpenCodePermissionPolicy`, `opencode-permission-policy.ts:51-61`, which requires the last matching `doom_loop` rule to be `ask`). If OpenCode 2 renames or drops `doom_loop`, launches fail closed, which is safe but blocks every session. Other rules such as `edit` and `bash` are written but not checked after translation. `mapModel` reads the cap from `options`, but 2.0.30 reports it under `body`, so the generation-budget assertion would misread it.
- Several callers run a bare `opencode` from PATH instead of the selected install: `opencode-cli-provider.ts:57` and `:97`, `account-pool/provider-account-binding-service.ts:120`, `worker-agent/worker-account-route.ts:182`, `shared/utils/opencode-account-login-command.ts:32`. Discovery (`opencode-cli-discovery-service.ts:180`) and region metadata (`opencode-region-model-metadata.ts:58-59`) use the PATH resolver and `models --verbose`.
- Sign-in builds `opencode auth login -p <provider>` (OpenCode 1 syntax). Per-account providers carry no key and rely on OpenCode's own key store (`opencode-account-provider-config.ts:1-15`).
- Updates: `cli-update-service.ts:72-77` reads npm `opencode-ai` and self-updates with `opencode upgrade`. The doctor suggests unpinned `npm install -g opencode-ai` (`provider-doctor-repair.ts:41`), while the launcher's error says `opencode-ai@1` (`opencode-cli-launch.ts:82`).

## Risks

- **OpenCode 2 is moving fast** (point releases most days). Pin the minimum version, keep fixtures from real output, and fail closed on unknown config shapes rather than guessing.
- **Shared database.** While OpenCode 1 and 2 both run, a future OpenCode 2 migration can break OpenCode 1 again. Mitigations: Decision 2, Phase 8, and the existing "No usable OpenCode install" diagnostics.
- **Desktop app version skew.** The desktop app's service is 2.0.18. Phase 1.4 keeps Harness off it entirely.
- **Command name clash.** Installing `@opencode/cli` replaces the OpenCode 1 `opencode` command. Phase 1.2 finds `opencode2`, and Phase 7.1 explains the clash.

## As-built notes

1. Decisions 1–4 use the recommendations: supported 2.x is preferred, 1.x remains a fallback, the normal shared database is retained, 2.0.30 is the minimum, and the major-install offer explains command replacement. No global CLI install or real key migration was performed.
2. The real 2.0.30 action map is `bash` → `shell`, `task` → `subagent`; `edit`, `external_directory`, `webfetch`, `websearch`, `question` and `doom_loop` retain their names, with none dropped. Configuration probes and final session startup use native 2.x configuration, ordered permission resources/action aliases, native provider/model metadata and body caps. The normalizer merges source documents before deriving numeric aliases, so later configuration cannot be hidden behind an earlier cap. Existing native provider models and agent instructions are preserved. Independent early review reproduced a wildcard permission gap; native action patterns now remain in their native namespace for assertions, with exact aliases confined to the legacy map. Real factory checks reject late shell/subagent wildcard allows; scoped denies and rule order remain intact.
3. Auth helper commands use the selected install and standalone JSON for 2.x. Custom credential identifiers absent from auth-list output are read with Node’s built-in SQLite reader using a bounded, names-only, read-only query. This avoids an Electron-native-module dependency in the standalone worker; actual pinned-Node and standalone executable probes passed without that native module, without modifying database bytes or creating a missing database. Sign-in hides terminal input and sends import JSON on stdin. A real isolated ACP prompt without an inline API key confirmed that the imported named placeholder credential reached the matching overlay provider (server recorded only a match boolean). Every generated sign-in route rechecks the actual stable version before any credential read or auth command, using the same parser as the launcher. This includes copied commands and legacy pickers; unsupported or replaced binaries refuse, and version probes have time/output limits. The repair prompt requires an explicit yes; automated helper processes use the OpenCode gate. User-run terminal commands run outside the app's in-process lock, as existing sign-in already did.
4. Real source and compiled factories start 2.0.30 through private ACP with no HTTP flags in isolated homes. Real native settings and caps round-trip. Compiled placeholder credential import, read-only identity lookup and metadata parsing passed repeated isolated runs. One earlier credential-name lookup returned empty before subsequent direct SQL and five repeated complete checks succeeded; no credential values were inspected, and failure remains closed. Cold regional metadata reads now use a temporary, secret-free activation overlay on the helper only, preserving existing configuration. Actual native catalog checks passed for all three regions, and actual source factory startup passed with only a named placeholder credential and no built-in regional login; no inference call was made.
5. Real 2.0.30 with a scripted localhost provider verified output-limit continuation (two parent model calls with the cap applied to both), aggregate turn usage and actual child metadata/child-usage exclusion. Actual isolated startup/load/resume/fork fixtures and local-model turn fixtures are sanitized and replayed by tests. Authenticated live-provider behavior is separately deferred.
6. Local full-tail idle forks clone on the source adapter under a prompt-admission reservation before opening the immutable child. The source keeps its identity and model configuration. Historical/edit/reset/unsupported forks and remote forks retain snapshot replay. No remote native source-clone operation is advertised.
