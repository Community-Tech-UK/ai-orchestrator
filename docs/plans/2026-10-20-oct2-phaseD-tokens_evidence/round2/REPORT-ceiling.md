## Behaviour delivered

### Step 1: Codex per-root-turn processed-token ceiling (Decision 16a)
* `codex/codex-turn-token-ceiling.ts` (pure): per-round counter, root and helper threads together; one wrap-up request at a time with bounded retries; stop returned once; counting never acts. `loop`, `plan-queue`, `automation`, `review` = Harness work (may be stopped); `chat` and ordinary helper `child` = chat group (wrap-up only; stop default 0).
* Four settings in all seven surfaces: `codexTurnCeiling{HarnessWork,Chats}{WrapUp,Stop}Tokens` = 150M / 300M / 150M / 0 (0 = off). Interface is a type-only module; `settings-defaults.ts` and `settings-metadata-runtime.ts` use literals (worker-closure rule). No migration needed: the store merges `DEFAULT_SETTINGS`.
* `codex/codex-turn-ceiling-controller.ts`: rounds, wrap-up (developer-role `thread/inject_items`, text contains "Wrap up now: report what is done and what is left."), stop (system notice, pause an active goal, interrupt running helper turns, then the root), root/helper share, bounded late corrections. Each round is bound to the root thread it ran on.
* Wiring: `codex-app-server-notification-adapter.ts` (live `thread/tokenUsage/updated`, helper completions, idle/late usage, root end-of-round usage) and `codex-app-server-turn-adapter.ts` (rollout reconciliation, stop throw, Codex-started rounds). A stopped round ends its send with the typed `HarnessStopError` (`shared/utils/harness-stop.ts`); the session stays usable, no duplicate error output. The fifth `requestContextWindow` argument of `usageAccounting.observe` is untouched at every call site (`codex-app-server-adapter.ts:331`, `codex-app-server-notification-adapter.ts:297`; receipt: `Grep usageAccounting.(observe|fallback)(`).
* The provider `error` event carries `details.stoppedByHarness`; the turn-ending classifier files it as `completed / harness_stop / autoContinueSuppressed`.
* Plan queue: `stopped-by-harness` park reason (contract, label), tracker outcome, worker / checker / triage parked on the first stop (no errored-round retry, no replacement worker, no triage retry), `runWorkerTurn` does not respawn; the stop is recorded FIRST in `parkUnlocked` and boot recovery finishes parking instead of respawning or re-judging (`plan-queue-park-policy.ts`, `plan-queue-recovery.ts`). Scheduled jobs: `automation-runner.ts` does not retry a Harness stop.
* **Remote Codex (windows-pc and other nodes):** a stop thrown on the worker crosses the RPC boundary with its own code (`RPC_ERROR_CODES.HARNESS_STOPPED`, -32006) and structured `data`; `worker-node-connection.ts` keeps `rpcCode`/`rpcData` on the error (message text unchanged); `RemoteCliAdapter.sendInput` revives the typed `HarnessStopError` (`remote-harness-stop.ts`) and emits `turn_error` first, exactly as a local adapter does, so the queue and automations behave the same as for a local session.
* Costs: `CostPurposeSummary.biggestTurns` (top 10, last 7 days) and `codexCredits`; `biggest-turns.component.ts` is included once on the Costs page. Codex rounds come from `turn-share` rows (helper part, stopped flag), other turns from per-turn cost rows now tagged with `sessionKind`; a Codex round is never listed twice.

### Step 2.3: root/helper share in the session-policy log
`event:'turn-share'` per thread+turn with `revision`; written when a round finishes and rewritten (max 3 corrections, debounced 3 s, flushed on shutdown and when the next round begins) when late child/rollout/idle receipts change it; written under the thread the round ran on even if the root was replaced meanwhile. `latestTurnShares` keeps the highest revision per thread+turn.

### Step 11.1: Codex thread-end credits
Installed Codex 0.163.0 supports `account/usage/read` (`threadId` in, `threadUsage.{estimatedUsageCreditsMicros, estimatedUsageUsdMicros, groups[]}` out), verified from the schema `codex app-server generate-json-schema` wrote to `_scratch/oct2-phaseD-round2/codex-schema/v2/GetAccountTokenUsageResponse.json` (no login, no network, no secrets).
* `codex-credit-reader.ts`: a defensive parser, a read hard-bounded to 2.5 s (request deadline plus a timer, cleared afterwards), and `CodexThreadCreditsLedger`: each root thread that ran a turn in this adapter is read at most once; a failed read is not retried.
* **Both ends of a root thread are covered:** `reopenAppServerThread` (an override in the notification adapter) reads the old root before the binding is replaced, then replaces it whatever the read did; graceful `terminate` reads the current root. A replacement thread that never ran a turn is not asked about. Forced `terminate(false)` skips the read, so forced shutdown stays fast.
* Rows (`event:'thread-credits'`) are cumulative per thread; readers keep the latest per thread (`latestThreadCredits`). The Costs page shows total credits, sessions, a dollar figure only where Codex gave one, split by kind.

### Telemetry reach (review point 5)
Codex adapters run in the Electron main process (local) or the worker-agent (remote node); the spawn-worker proxy is Gemini-only. Local: the adapter writes the real log (proved with the unmocked writer via `AIO_SESSION_POLICY_DIR`). Remote: `session_turn_share` / `session_thread_credits` are forwarded by `worker-instance-telemetry.ts`, validated by strict zod in `instance-telemetry-rpc.ts`, and written in the main process by `RemoteCliAdapter` -> `remote-session-telemetry.ts` under the controller's own instance id; replay-safe. Publishing cannot throw into a turn or a shutdown.

### Exec (command) mode: the real capability limit (not covered, not relaxed)
The ceiling reads the live app-server token feed. Command mode (`codex exec`, always used for hardened sessions and the fallback when the app server is unavailable) reports usage only in the final `turn.completed` event (`exec-transcript-parser.ts`), so there is nothing live to act on. Nothing was built to poll, hardened mode and permissions are unchanged. What is done: (1) the four settings' descriptions say it; (2) the first send in command mode logs a warning when any limit is configured; (3) for Harness work that promises a stop, one transcript line says "This session's token limit can't act during a turn: Codex is running in command mode, which reports its token use only when a turn ends." (`hardened` is in its metadata); chats get the log line only; (4) `docs/architecture.md` states it. Tests: adapter spec "command mode has no live token feed", settings spec, controller spec (a failing notice cannot break the send).

## Real limitations and open items
* Credits and the stop need the app-server: a forced termination, an app-server that died, an unsupported Codex, an API-key login (no billing route, `threadUsage` null) or a thread that never ran a turn here has **no reading and none is invented**. Rounds still pending a 3 s correction are lost if the process is killed.
* Exec/command mode (hardened sessions, app-server fallback): ceiling, share rows and stop do not exist there; stated in the settings text, log, one transcript line and the architecture doc.
* Loops and reviews: a Harness stop arrives as a failed send/iteration under their existing failure and cap rules (only the plan queue and scheduled jobs have special handling, as the plan says).
* Version skew on remote nodes: a worker with this change talking to a coordinator without it gets an unknown RPC code (-32006) and drops the new telemetry events with a warning, so the stop looks like an ordinary failed send there. Update both ends together.
* `recordSessionPolicy` (thread-start policy rows in `codex-thread-requests.ts`) still no-ops on a worker node (pre-existing); my rows carry the trial arm and hashed key themselves.
* A live check of a real round past 150M / 300M cannot run here; everything is driven through the real adapter with fixture notifications.
* No new approval gate; no change to the isolation guard, hardened mode or permissions; no polling subsystem; no root planning doc touched.
