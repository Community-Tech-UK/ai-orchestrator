## Round 13 (verifier round 2 of 3: Windows worker cannot reach the PC copy's coordinator)

Cause found by reading the code: `start --pc` runs the copy in the PC's Linux space (only `--windows` runs it on the desktop), and the Windows-side script in `scripts/remote-checks/remote-run.sh` probed only Windows 127.0.0.1, which reaches a Linux-space port only through WSL localhost forwarding. I could not observe the PC's WSL settings, so the exact reason forwarding failed is unconfirmed (candidates: forwarding off, mirrored mode, port in a reserved range). The worker was also reaching the probe after writing its config.
Fix (scripts/remote-checks/remote-run.sh): the Windows script takes `-LinuxAddress` (first non-loopback IPv4 from `hostname -I` in the Linux space, "none" otherwise, start only), probes 127.0.0.1 then that address, and writes the first that answers into the worker's `coordinatorUrl`; the probe now runs before the config is written; the already-joined check accepts any IPv4 host for the same port; failure message lists what was tried. The copy listens on 0.0.0.0, so the Linux address works when forwarding does not. Help text in dev-app.js updated. Test added in dev-app.spec.ts (start passes -LinuxAddress, stop passes none).
