## Goal

Let a Codex session create an origin-bound Instagram login in the configured Bitwarden Agent Credential Vault and fill it into an authorised extension-driven Chrome tab on `windows-pc`, without exposing the generated password to the model or weakening the existing origin, vault-folder, grant, or escalation boundaries.

## Design

### Codex tool surface

Codex receives the full Browser Gateway tool surface eagerly on the initial MCP handshake. Other providers retain the existing deferred surface. This is an AIO-side compatibility policy at the bridge-config boundary, because the dynamic `functions.exec` registry is owned by Codex and cannot be mutated by this repository after a `tools/list_changed` notification.

This makes the normalized Codex functions, `ALL_TOOLS`, and the MCP list agree from the first execution cell. Reconnects and forwarder restarts recreate the same eager surface and therefore do not depend on reveal persistence for Codex. The Browser Gateway's deferred reveal and continuity behavior remains unchanged and tested for clients that support it.

### Vault credential creation

`browser.create_agent_credential` gains optional non-secret metadata:

- `itemTitle`: the exact Bitwarden item title.
- `loginUri`: the intended credential login URI.

When `loginUri` is present, its normalized origin is the credential origin used for the register-authorisation check and the vault binding. The current tab is used only to resolve the stable credential-authorisation scope: the managed profile id, the remote worker node id, or `local` for a coordinator extension tab. The live Meta origin does not become a permitted fill origin.

For backward compatibility, calls without `loginUri` continue to derive the credential origin from the live target.

Creation on an extension target is permitted only when a live `register` credential authorisation covers the resolved node scope and the explicit credential origin. The creation operation never returns the generated password and never fills or submits a page.

An extension-shaped profile id may never fall through to the managed-profile driver. The exact profile/target pair must first exist in the trusted extension tab store and answer a fresh snapshot. This liveness proof happens before stable-node scope resolution or any register-authorisation lookup.

### Extension-driven fill

The existing secure fill path remains authoritative:

1. The operator-only `browserAllowSharedTabCredentialFill` switch must be enabled.
2. A live `login` credential authorisation must cover the stable node scope and the current page origin.
3. The vault item must be inside the Agent Credential Vault folder and bound to that exact origin.
4. The extension tab origin is refreshed before authorisation and immediately before every secret field is typed.
5. The secret travels only through the trusted in-process vault resolver and authenticated Browser Gateway/worker extension channel. It is never a model-facing tool argument or result.
6. For extension targets, the worker performs a secret-free all-frame origin probe, sends the secret only to exact-origin frame IDs, rechecks the top-level origin immediately before dispatch, and rechecks `location.origin` inside the isolated injected function before touching the DOM. Secure type results contain only non-secret status.
7. Before any extension-target vault value or mailbox code is resolved, the exact local/remote extension channel must have fresh runtime evidence at or above the secure protocol floor. The check repeats immediately before sensitive dispatch, and the main process accepts only the exact fixed two-field taint completion for password/secret writes. Missing, stale, malformed, old, legacy, or extra-field responses fail closed.
8. Runtime evidence is generation-monotonic: older delayed messages cannot replace newer evidence, and incomplete or inconsistent evidence for the current generation remains untrusted until a newer generation appears. The exact authenticated poll must independently prove a compatible runtime before the command store dequeues any origin-bound non-public write; otherwise the poll receives no command and the caller gets a fixed non-secret failure.
9. A sensitive write persists an origin-wide observation taint before secret injection. Current and future same-origin tabs, opener descendants, and tabs embedding a tainted-origin frame inherit that taint; closing the original tab does not declassify the origin. Autonomous tab-payload captures and taint setup are serialized so a capture cannot straddle secret injection. Tainted payloads expose only the canonical origin, a fixed title, empty text, and a fixed block reason; screenshots and page-controlled URL/title/text are suppressed.

An Instagram credential created from a Meta tab is still bound to `https://www.instagram.com`. It can be filled on Instagram, but not into Meta or any unrelated origin. This models the Meta-to-Instagram workflow without a general cross-origin secret-fill bypass.

### Non-secret result

Successful creation returns only:

```ts
{ vaultItemRef: string; username: string }
```

The password must not appear in MCP content, errors, audits, journals, traces, snapshots, logs, or test output. Bitwarden command failures must not echo secret-bearing command arguments or stderr that could contain encoded item bodies.

### Escalations and submits

This change does not automate account submission. CAPTCHA, unavailable 2FA/verification codes, legal declarations, and other existing hard stops continue through Browser Gateway escalation/approval handling. Mutating commands retain the existing receipt/read-back behavior and are not blindly retried after ambiguous execution.

## Acceptance criteria

1. A Codex Browser Gateway session starts with normalized callable wrappers for all Browser Gateway tools, including credential, accessibility, query, grant, and preflight tools.
2. `ALL_TOOLS`, the callable `tools` object, and the user-visible schema agree from the initial cell and after reconnect/restart.
3. Other supported providers retain deferred Browser Gateway schemas.
4. A register-authorised extension target can create an Instagram-bound vault credential with the requested title, username, and login URI.
5. Creation fails closed without the correct node-scoped register authorisation.
6. The created credential can be filled only on its exact bound Instagram origin and only when the shared-tab opt-in plus login authorisation are present.
7. No model-visible response, error, audit, journal, trace, or snapshot contains the generated password.
8. Opaque references cannot resolve secrets through any model-facing tool.
9. CAPTCHA, 2FA, legal-declaration, and ambiguous-submit safeguards remain unchanged and passing.
10. A live `windows-pc` smoke test discovers the secure tools and reaches the expected authorisation/approval boundary without creating a real Instagram account.

## Out of scope

- Controlling the Bitwarden UI.
- Returning or accepting raw passwords through browser/computer tools.
- Changing the operator-only shared-tab credential-fill setting automatically.
- Creating the real 12 Steps Instagram account during infrastructure verification.
- Patching or replacing the installed Codex CLI's internal dynamic tool registry.
